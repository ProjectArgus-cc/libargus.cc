# v1.7.5 implementation plan

Status: implemented in the working tree; local validation is recorded in [v1.7.5 validation](../v1.7.5-validation.md). The eight-target hosted matrix and actual publication remain required release gates. No release has been published by this pass.

Audit baseline: `f3239975e18021b8aaa30bb00441af5e04578759` (`v1.7.4`). Prepared 2026-09-09.

The objective is to restore release execution, establish that verified artifacts are the published artifacts, and close the associated concurrency, buffer-lifetime, and CPU-portability gaps. Preserve the existing Java API, existing C entry points and layouts, eight native modules, and JDK 22 minimum. Any new C functions are additive.

## Scope and design decisions

| Area | Decision for this pass |
| --- | --- |
| Release identity | Finalize one candidate; verification and publication consume its existing files. Publication cannot compile, package, or reconstruct JARs. |
| Validation | Reuse the same validation implementation from PR CI and releases. A release requires the complete graph for its resolved tag commit. |
| Platform contract | One checked-in catalog defines the eight targets, resource paths, expected masks, public filenames, and supported CPU/toolchain baselines. |
| Projector sharing | Support sharing a projector across text contexts, with exclusive access to its mutable encoding/output state. Distinct projectors retain independent concurrency. |
| Java buffer lifetime | Expose borrowed buffers directly to FFM downcalls instead of hiding their addresses inside struct arguments. Preserve the legacy C batch API. |
| Portable builds | Proposed distribution baseline: x86-64-v3 on Linux/Windows and the supported generic AArch64 baseline on macOS. Enforce the baseline across dependencies; do not infer compatibility from the runner CPU. |
| Diagnostics | Add bounded build-identity introspection and structured verification results. Keep initialization, device availability, and successful accelerator execution distinct. |
| Performance claims | Document and measure specific allocation behavior. Do not claim that frame wrappers, strings, or scoped Java objects categorically allocate nothing. |

Broad loader cache/search-path redesign, new accelerator families, new model architectures, sampler redesign, dynamic CPU backend plugins, and a new public ABI generation framework are outside this pass. Required fixes found while proving the listed contracts remain in scope. Optional GPU hardware testing must never be represented as completed when hardware is unavailable.

The CPU baseline is an explicit proposed product choice, matching the existing Linux portable flag's intent. Validate MSVC and upstream mappings before encoding it; an incompatible dependency setting is a build failure, not permission to silently raise the baseline.

## 1. Establish the release contract and restore workflow preparation

Primary files: `.github/workflows/*.yml`, `scripts/release/`, a new platform catalog, `.github/dependabot.yml`, and `version.txt`.

1. Define a validated catalog for the existing eight targets. Include module ID, OS/architecture, backend, native resource path, library basename, exact feature mask, public archive filename, and toolchain/baseline identity. Expected masks are CPU `1`, CUDA `3`, ROCm `5`, Vulkan `9`, and Metal `17` under the current ABI constants. Cross-check the catalog against those constants rather than duplicating unchecked mappings.
2. Replace the invalid Action pins with full commits verified against their upstream repositories. Pin the other direct external Action references, including first-party Actions. Resolve annotated release tags correctly; never derive a full SHA from an abbreviated hash.
3. Add workflow syntax/expression linting and an independent Action-reference check on pull requests. Validate full SHA syntax, repository and commit existence, Action subpaths, and documented tag correspondence. Handle local reusable workflows separately; reject unsupported reference forms explicitly. Network errors and rate limits cannot become a successful release check.
4. Run the same reference validator in the release preflight and provide a local pre-tag entry point. The validator workflow must not depend on the suspect third-party Actions it checks. Dependabot proposes routine pin changes.
5. Make release preflight resolve a real tag and require agreement among its commit, checkout commit, requested version, `version.txt`, and publication coordinates. Manual dispatch must identify an existing tag; the current unused version input cannot select arbitrary release bytes.
6. Give build and verification jobs read-only repository permissions. Grant signing and publication credentials only to their respective trusted jobs; remove blanket write permissions and avoid `secrets: inherit`.

Acceptance: an invented SHA, mismatched tag comment, malformed workflow, missing platform, duplicate target, or version disagreement fails before release construction. Repository protection configuration must be checked separately: a workflow file alone does not enforce tag creation policy. Confirm whether existing branch/tag rules actually require the relevant checks.

## 2. Make native builds portable and diagnostically identifiable

Primary files: `CMakeLists.txt`, `build.gradle.kts`, `include/libargus.h`, `src/argus_common.cc`, Java bindings, and generated build metadata.

1. Apply portable configuration before upstream `FetchContent` configuration. Disable `GGML_NATIVE` for distribution builds and explicitly constrain applicable SIMD features in the wrapper and compute dependencies. Correct `/Oarch:AVX2` to the supported MSVC option and inspect the complete MSVC feature set.
2. Ensure Gradle declares backend and portability selections as task inputs. Changing CPU/CUDA/HIP/Vulkan/Metal settings must invalidate configuration and compilation rather than reusing an old CMake result. Use deliberate build-directory identities where necessary.
3. Resolve the existing llama.cpp and whisper.cpp versions to immutable commits without combining this pass with an upstream upgrade. Record resolved revisions, compiler/toolkit identity, target architecture, and CPU baseline. Verify the Gradle distribution checksum as part of the build toolchain contract.
4. Add an additive, bounded C build-information query and a Java value representation containing version, source revision, upstream revisions, compiled feature mask, architecture, CPU baseline, and ABI schema identity. Generate native and packaged expectations from build inputs. Local builds may report a clearly marked unknown/dirty identity; release builds may not.
5. Check native struct sizes, offsets, and alignment against Java layouts. Record ABI identity separately from backend identity. Do not treat matching version text as proof of compatible layouts or matching bytes.
6. Keep new diagnostic downcalls outside the critical-downcall allowlist. Exclude test instrumentation from public release exports and inspect the final symbol surface, including symbols introduced by static dependencies.

Acceptance: fresh portable builds contain no unintended host-specific compiler options; switching backend settings changes the actual build; diagnostics identify the compiled inputs. Execute CPU smoke tests under a constrained supported CPU model where feasible. Compiler-flag inspection alone is not a demonstration that every linked instruction satisfies the baseline. Record the minimum supported OS/runtime dependencies alongside the CPU requirements.

## 3. Close shared-projector concurrency and failure-state gaps

Primary files: `src/argus_multimodal.cc`, `src/argus_internal.h`, `include/libargus.h`, and native/Java multimodal tests.

1. Add synchronization to the projector wrapper for mutable upstream encoding state. Protect the entire encode-to-embedding-consumption interval; locking only `mtmd_encode_chunk()` would leave its output vulnerable to replacement while a text context consumes it.
2. Define a consistent native lock order for projector and text context and apply it to every path needing both. Keep Java resource leases as lifetime protection; they do not replace native execution locks. Document the C caller's obligation to keep handles alive during calls.
3. Audit other accesses to projector state against the pinned upstream implementation. Preserve concurrency for upstream operations explicitly documented as safe; avoid a process-global lock.
4. Validate model/projector association, sequence ID, counts, batch size, and position boundaries before state mutation. Reject negative bitmap counts before conversion to container sizes. Keep error-output behavior explicit.
5. Exercise multimodal success, partial failure, and exceptions against pending sampler state, logits ownership, and KV state. Prevent failed evaluation from making stale logits appear usable. Define when output positions are published and what partial work callers must discard.
6. Extend factory exception-safety checks to every retain/allocation/initialization transition touched by this pass, including failure after retaining the base model. Resource cleanup must remain transactional.

Acceptance: same-projector evaluations through different text contexts cannot overlap protected state; different projectors can make independent progress; multimodal evaluation excludes competing text/KV mutation on the same context. Invalid arguments leave state unchanged, and interrupted evaluation cannot publish successful output or valid stale logits. Allocation failures release each acquired resource exactly once.

## 4. Make Java borrowed-buffer lifetimes visible to FFM

Primary files: `include/libargus.h`, `src/argus_text.cc`, `ArgusContext.java`, `ArgusBindings.java`, `ArgusValidation.java`, and FFM tests.

JDK 22 guarantees lifetime and thread-access checks for `MemorySegment` arguments mapped to address parameters, including preventing shared-arena closure during the downcall. It cannot infer the ownership of an address embedded in another segment. An `isAlive()` precheck alone does not close the race. See the [JDK 22 Linker contract](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/foreign/Linker.html).

1. Add a C decode entry point accepting the token segment and scalar batch fields directly. Route it and the existing `argus_decode_batch()` through one native implementation so validation, cancellation, locking, and sampler transitions cannot drift.
2. Route existing high-level Java `decodeBatch` methods through the direct-argument binding. Retain context/abort resource leases for the full operation. Remove shared batch scratch and its lock only where the new call no longer needs them.
3. Preserve the legacy C entry point and clearly document raw-pointer lifetime obligations. Existing unsafe Java handle overloads do not become safe merely because the preferred overload is fixed.
4. Audit other nested-pointer argument paths. Use direct FFM arguments for independently owned borrowed memory; retain owned native resources through leases. Do not introduce internal JDK scope APIs or copy token tapes to conceal lifetime gaps.
5. Strengthen buffer validation for native storage, required capacity, element alignment, writability where relevant, and explicit zero-length semantics. Avoid requiring writable memory for read-only token inputs.
6. Correct concurrency fixtures to use shared arenas for intentionally shared buffers. Add separate cases proving that confined buffers are rejected on the wrong thread.

Acceptance: on JDK 22 and JDK 25, closed/confined/undersized/misaligned inputs fail before unsafe native access. A shared-arena close attempted while the real downcall is held open is safely rejected according to the JDK contract; it succeeds after the call exits. The public abort-object overload is exercised directly. Decode results and sampler state remain equivalent through both C entry points, without an added token-buffer copy.

## 5. Give lifecycle and media tests deterministic failure detection

Primary files: `tests/`, Java test sources, and test-only native build configuration.

1. Keep `TestNativeResource` for base lifecycle mechanics, and add tests through public composite operations for abort/decode, multimodal evaluation/chunks, vocoder use, and video ownership. A manually held lease cannot stand in for the public operation under test.
2. Use private test observers or test-only native adapters at actual operational boundaries. Observe that the competing thread reached the contended acquisition, not merely that its thread started. Use bounded timeouts for deadlock detection, with unconditional barrier release and worker cleanup in `finally`/RAII paths.
3. Instrument the production wrapper's lock/state/ownership paths in a separate test build. Inject evaluator/iterator behavior beneath those paths; do not replace the locking wrapper with a fake or reintroduce a test function into the release C ABI. Production builds must have no test callback branch or test-exported symbol.
4. Rename the current text query/decode contention test accurately. Add multimodal cases for both shared text-context contention and shared-projector contention. A text-only chunk test cannot establish media encoding safety.
5. Provide deterministic iterator items for mandatory ownership/concurrency tests on Linux, Windows, and macOS. Verify exact-once delivery by item identity, ordering at the iterator's serialization point, EOF behavior, read/close exclusion, and exact resource releases. Completion order across worker threads need not equal iterator order.
6. Add a small generated video for actual FFmpeg iteration and a pinned compatible model/projector fixture for at least one mandatory CPU media integration lane. Audit fixture feasibility, size, hash, and redistribution terms first. If no small projector is feasible, use a bounded cached larger fixture; missing prerequisites fail that lane rather than reducing it to a null-input test.
7. Add Linux CPU ASan/UBSan coverage and targeted TSan coverage. Keep sanitizer runtimes separate from published artifacts. Scope upstream/runtime suppressions narrowly and document their evidence.

Required fault demonstrations include removing the projector/context lock, omitting a dependency lease, freeing a retained resource early, duplicating/dropping an iterator item, and failing an allocation after retain. Each relevant test must fail for its intended reason. Keep these targeted fault demonstrations separate from routine regression runs.

## 6. Construct and verify one immutable candidate

Primary files: `build.gradle.kts`, module build files, `scripts/release/`, classifier verification code, and release workflows.

1. Build the eight native targets through reusable validation. Run native and Java integration checks against explicitly selected native libraries, including CPU execution where accelerator hardware is absent. Diagnose the separate ROCm CI failure from actual logs; do not assume repairing Action pins resolves it. Install only each lane's required toolchain/runtime dependencies.
2. Select native workflow artifacts explicitly by the catalog and immutable artifact IDs. Check the exact directory/file set, architecture, expected exports, runtime dependencies, and feature identities. Reject ambiguous `find | head` selection and artifact namespace contamination.
3. Package Java modules in a fresh workspace with a dedicated assembly task. Run core integration tests in an explicit native-equipped validation task; do not accidentally run them with no native provider during packaging. Do not solve this by weakening the required test graph.
4. Stage exactly 27 JARs: runtime, sources, and Javadoc for each of nine modules. Reject duplicate basenames, unexpected versions/modules, missing files, duplicate ZIP entries, invalid resource paths, or extra native payloads. Minimum size is only a sanity check.
5. Produce the complete Maven repository payload, including the exact POM, metadata, signatures, and checksum set selected by the publication contract. Use current Gradle/NMCP construction facilities where supported; inspect the pinned plugin's actual tasks before integrating. Trusted signing finalization adds signatures/checksums without regenerating any JAR. PR candidates use an explicit unsigned validation mode; release candidates require valid signatures.
6. Create a Central bundle from that finalized Maven tree. Create eight uniquely named standalone native archives from the same binaries embedded in the classifier JARs. Archive contents and extracted native bytes are both inventoried.
7. Seal a candidate manifest containing source/version identity, the exact file set, sizes and streaming SHA-256 digests, Maven coordinates, backend/resource mapping, and build identities. Hash the completed Central bundle as well. Avoid recursive hashes: the bundle contains Maven payloads, and its enclosing manifest is outside the bundle.
8. Verify each of the eight final classifiers in a fresh JVM on its target OS. Use exactly the designated core and classifier JARs, a controlled working directory/environment, and a fresh extraction location. Assert selected provider, actual loaded-library origin and digest, embedded-native digest, ABI/build identity, and full feature-mask equality. Eliminate accidental success through a local native fallback in this verification mode without changing normal loader policy.
9. The verifier emits a bounded structured receipt tied to candidate-manifest digest, core/classifier/native digests, source SHA, target, and result. Negative verification must report a specific feature-mismatch outcome; crashes, missing libraries, timeouts, and other JVM failures are failures of the test.
10. Aggregate all expected receipts and reject missing, duplicate, skipped, or mismatched lanes. Exercise final CPU classifier JARs through representative Java native operations in addition to the build-feature probe. A feature mask proves compiled support, not successful GPU inference.

Proposed GitHub asset contract: 27 JARs, eight platform/backend native archives, `manifest.json`, and `checksums.txt` (37 uploaded assets, excluding GitHub's generated source archives). Public JAR exports must match the Maven entries byte-for-byte. The checksum file covers distributables and the manifest, excluding itself; the manifest does not hash itself. Any additional public signature/provenance asset requires an explicit contract update.

Acceptance: wrong masks, missing CPU bits, unknown bits, wrong providers, substituted natives, incompatible ABI, duplicate ZIP entries, wrong versions, missing JARs, and a one-byte candidate mutation are all rejected. Every standalone native matches the corresponding JAR payload. Every release receipt identifies the same sealed candidate.

## 7. Publish without rebuilding and recover partial releases safely

Primary files: release workflows and narrowly scoped transport/status code under `scripts/release/`.

1. Make publication depend on native/Java validation, required sanitizer/media lanes, candidate finalization, all eight classifier verifiers, and receipt aggregation for the exact tag commit. Require explicit success for every required job; an absent or unexpectedly skipped check cannot satisfy the gate.
2. Use per-version release concurrency that prevents simultaneous publishers without cancelling an active publication. Validate credentials/configuration before starting external publication.
3. Let the publisher consume only the sealed candidate and its receipts. It must have no Gradle task graph capable of compiling, running JAR tasks, generating documentation, or replacing verified payloads. Recheck the file inventory and hashes immediately before transport.
4. Upload the completed bundle through the Central Publisher API. Track the deployment ID, wait for validation, and publish only the verified candidate. Poll to an explicit terminal state with bounded retries/timeouts. `VALIDATED` and `PUBLISHING` are not `PUBLISHED`. The API supports bundle upload, status queries, and explicit publication of a validated deployment; see [Sonatype's API contract](https://central.sonatype.org/publish/publish-portal-api/).
5. Stage the GitHub release as a draft. Verify its exact asset set and downloaded hashes before making it public. Confirm Central publication and retrieve the served Maven payloads for digest comparison, allowing bounded propagation delay. Release notes report device-execution coverage honestly.
6. Preserve GitHub Packages as a separately reported secondary destination using the same finalized Maven payloads. Do not classify every publication error as "already published." Existing coordinates are acceptable only after their contents match; conflicting bytes are a hard failure.
7. Record destination state and candidate identity durably. On uncertain upload responses, reconcile existing deployments/assets before retrying. A partial publish is resumable only from the same retained candidate; rebuilding the same version is not a recovery strategy. Preserve candidate artifacts long enough for recovery and document how to retrieve them.
8. Never overwrite conflicting bytes or move an already published tag. Central and GitHub do not offer a distributed atomic transaction: report partial completion accurately and complete the missing destination from the original candidate.

Acceptance: upload failure, missing credentials, delayed propagation, a timeout after accepted upload, and partial destination success all produce distinct, recoverable states. Reruns converge on identical bytes or fail on conflict. The repository's existing source-only v1.7.4 release is not represented as a successful binary release.

1. Update README installation/build commands and describe the actual CPU, OS/runtime, ownership, concurrency, cancellation, and publication contracts. Correct the documented default CPU build to match CMake behavior.
2. Replace or retire the stale `scripts/package-artifacts.sh` mappings in favor of the catalog-backed implementation. Keep release tooling modular: catalog/schema, inventory/hashing, receipts, and destination transport have separate responsibilities.
3. Document build-information and verifier output. Separate metadata inspection from backend initialization and optional device execution; avoid adding GPU initialization to a simple build query.
4. Reconcile zero-allocation statements with specific operations. Profile steady-state decode/sample and video iteration after warmup, distinguishing Java heap, native allocations, setup cost, and unavoidable media objects. Use observed allocations to guide narrowly scoped improvements; do not promise a universal allocation-free API or infer performance from code coverage.
5. Update release notes/version examples only when the implementation and release candidate agree. Include a maintainer recovery procedure and clearly distinguish source tag, validated candidate, Central publication, and public GitHub release.

## Verification matrix and completion criteria

| Layer | Required execution |
| --- | --- |
| Workflow/release tooling | PR and tag preflight; offline malformed/duplicate/conflict fixtures; live Action-reference checks |
| Native distribution | All eight targets compile and load; exact masks, architecture, symbols, dependency and build-identity checks |
| CPU behavior | Linux/Windows CPU native integration; Java native integration on supported OS families; constrained-CPU smoke where available |
| Java FFM | JDK 22 minimum and JDK 25; actual direct-argument lifetime and public composite-operation tests |
| Media/lifecycle | Production-wrapper tests on all OS families; at least one mandatory real media/projector integration lane |
| Sanitizers | Linux CPU ASan/UBSan and focused TSan; no sanitizer/test payload in release artifacts |
| Final artifacts | Eight isolated classifier JVMs, positive and specific negative cases, exact receipts and native/JAR/bundle identity |
| Publication | Offline/fault-injected transport rehearsal, then destination status and served-byte verification during an authorized release |

Run focused failing cases after each fix, then the affected suite. Run the full required matrix once the integrated changes are ready; repeat broader checks only for changes or unresolved failures that justify them. Redirect verbose build/test logs to files and summarize actionable failures. Do not use test counts or coverage percentages as completion evidence.

Implementation is complete when the required behavioral and artifact checks pass and a publication-ready candidate can be constructed and verified without rebuilding it. Release completion additionally requires actual destination publication and digest verification; preparing this plan or passing a dry run does not establish that outcome.
