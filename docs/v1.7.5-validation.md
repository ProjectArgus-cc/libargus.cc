## Allocation observation

`AllocationProbe.java` uses HotSpot's per-thread Java allocation counter, warms
2,000 one-token decode/sample iterations, then measures 2,000 more. KV cleanup is
outside the measured decode/sample interval. Video measurements use the public
`readNext()` API, after 20 complete-video warmups, over 20 further videos including
EOF reads. Setup, model quality, GPU inference and native allocation rates are
outside this measurement.

| JDK | Decode Java bytes/call | Greedy sampling Java bytes/call | Video Java bytes/read |
| --- | ---: | ---: | ---: |
| Temurin 22.0.2 | 0.44 | 0.00 | 821.76 |
| Temurin 25.0.2 | 0.44 | 0.00 | 1088.16 |

These are observed averages for the synthetic CPU workload, not API guarantees.
JIT state and workload change allocation behavior. Native decode still allocates
batch storage; persistent samplers reuse state but reconfiguration/rollback may
allocate. Video strings, wrappers and scoped objects are not universally free.

Example reproduction after building the core JAR and placing FFmpeg on PATH:

```bash
java --enable-native-access=ALL-UNNAMED \
  -Dcc.projectargus.libargus.path="$PWD/build/lib/libargus.so" \
  -cp bindings/java/libargus-core/build/libs/libargus-core-1.7.5.jar \
  scripts/AllocationProbe.java tests/data
python3 scripts/release/mutation_check.py native /tmp/argus-native-faults
python3 scripts/release/mutation_check.py java /tmp/argus-java-faults
```

## Required hosted validation and release work

The eight-target Windows/macOS/Linux accelerator matrix has **not** executed from
this unpushed checkout. Consequently this pass does not claim a validated complete
release candidate, successful GPU inference, or published Maven/GitHub bytes.
Those remain mandatory workflow gates and destination checks.

The separate observed ROCm failure was HIP 6.1 rejecting floating-point aggregate
zeros in raw BF16 lanes in pinned llama.cpp `mma.cuh`. A guarded, idempotent vendor
patch changes those zeros to integer zeros without changing their representation
or suppressing the compiler diagnostic. The ROCm lane must still compile it on
its actual toolchain. CUDA 12.4.1's compiler check uses NVCC 12.4.127, as documented
in [NVIDIA's component table](https://docs.nvidia.com/cuda/archive/12.4.1/cuda-toolkit-release-notes/).

The hosted graph must prove each final classifier against the same sealed signed
candidate before publication. Real destination credentials, acceptance by Central,
propagation, and served-byte verification are exercised only during an authorized
release. Recovery is documented in [release operations](release.md).
